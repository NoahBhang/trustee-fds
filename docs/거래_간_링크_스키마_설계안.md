# 거래 간 링크 스키마 설계안

## 자금 환류·연쇄 거래를 표현하기 위한 `transaction_links` 테이블

**작성일:** 2026년 9월 3일
**문서 성격:** 설계 제안 (로드맵 4단계). 구현 전 검토용.
**관련:** `priority_signals.funds_circled_back`, `src/engine.py` `_p6`, README §8

> **주의:** 이 문서는 설계안이다. 스키마는 아직 구현되지 않았고, `funds_circled_back`
> 술어는 현재 무조건 `False` 를 반환한다.

---

## 1. 문제

`art391_4_gratuitous.yaml` 의 우선순위 신호 `funds_circled_back`("거래 직후 자금이
관계인에게 환류")은 거래와 거래를 잇는 자료 구조가 없어 탐지할 수 없다.
`engine.py` 의 `_p6` 는 다음과 같다.

```python
@predicate("funds_circled_back")
def _p6(c):
    # 거래 간 연결 테이블이 아직 없다. 로드맵 4단계.
    return False
```

샘플의 T021 은 "T001 직후 조카 계좌 경유 자금 환류 의심"이지만, 개별 거래로만
보면 T001(배우자에게 매각)과 T021(배우자에게 증여)이 별개로 처리된다. 두 다리가
하나의 조율된 이전이라는 사실을 담을 자리가 없다.

개별 거래는 각각 방어 가능해 보이는데 연쇄 전체가 설계를 드러내는 것이 전형적인
환류 패턴이다. 그 연쇄를 표현하는 것이 이 테이블의 목적이다.

---

## 2. 설계 원칙 (기존 3원칙의 연장)

**링크는 "관찰된 사실"만 담고 "환류다"라는 결론은 담지 않는다.**

`action_type` 이 `sale` 이지 `undervalue_sale` 이 아닌 것과 같은 원칙이다.
`link_type` 은 `fund_trace`(A의 자금이 B의 재원이 되었다)라는 사실이지
`circular_laundering`(자금세탁 순환)이라는 결론이 아니다. "환류" 판정은 룰이
`fund_trace` + 양 끝단이 관계인 + 짧은 시간창을 보고 내린다.

`parties.csv` 가 "배우자다"라는 사실만 담고 특수관계인 해당 여부는 룰이 판정하는
것과 같은 구조를, 거래 간 관계에도 적용한다.

---

## 3. 테이블 정의: `transaction_links`

거래와 거래를 잇는 **간선(edge) 테이블**. 한 행이 링크 하나.

| 컬럼 | 타입 | null | 설명 |
|---|---|---|---|
| `link_id` | str | ✗ | PK. 예: `L-001` |
| `case_id` | str | ✗ | → `cases.case_id`. 양 끝 거래의 `case_id` 와 반드시 일치 |
| `from_transaction_id` | str | ✗ | → `transactions.transaction_id`. 시간상 앞선 다리 |
| `to_transaction_id` | str | ✗ | → `transactions.transaction_id`. 뒤따르는 다리 |
| `link_type` | enum | ✗ | 사실 유형 (§3.1) |
| `intermediary_party_ids` | str | ✓ | → `parties.party_id` 의 `;` 구분 목록. 경유 계좌·경유인 (예: `P-006`) |
| `value_traced` | num | ✓ | 링크를 따라 추적된 금액. **null = 미상.** `asset_fair_value` 결측 정책과 동일하게 0으로 대체하지 않는다 |
| `trace_method` | enum | ✓ | `account_records` / `registry` / `instrument_no` / `statement` / `circumstantial` |
| `confirmed` | Y/N | ✗ | 증거로 확립됐는가. `suspension_date_confirmed`·`payment_verified` 와 같은 축. "의심"은 `N` |
| `source` | str | ✓ | 증빙 문서 |
| `note` | str | ✓ | |

**저장하지 않는 것**: `elapsed_days` 같은 파생값. 두 `transaction_date` 로 실행 시
계산한다 (기존 스키마의 "파생 필드는 저장하지 않는다" 원칙 — 지급정지일이 바뀌면
즉시 낡는다).

### 3.1 `link_type` 값 (사실만 열거)

| 값 | 사실 |
|---|---|
| `fund_trace` | A 에서 나온 금전이 B 의 재원이 됨 |
| `shared_asset` | 동일 물건이 두 다리를 통과 |
| `same_instrument` | 동일 어음·수표·계좌 |
| `contingent` | B 가 A 를 법적 조건으로 함 (보증 + 구상약정 등) |
| `substitute` | B 가 A 를 대체·취소 |

`circular_transfer`, `sham`, `laundering` 같은 결론 값은 두지 않는다.

### 3.2 다중 경유가 많아지면 (선택적 정규화)

`intermediary_party_ids` 구분 문자열이 부담되면
`transaction_link_hops(link_id, hop_seq, party_id, account_ref)` 로 분리한다.
Phase 1 샘플 규모에서는 구분 문자열로 충분하고, `expected_flags` 가 이미 `;`
구분을 쓰므로 관례가 일치한다.

## 4. 기존 4개 테이블과의 연결

```
                  ┌──────< transaction_parties >──── parties
                  │                                    ▲
  cases ──< transactions                               │
              │   ▲  ▲                                 │
              │   │  │  from_transaction_id            │
              │   │  └──────────────┐                  │
              │   │  to_transaction_id                 │
              │   │                 │                  │
              │   └──── transaction_links ─────────────┘
              │              │      intermediary_party_ids
              └──────────────┘ case_id
```

- `transaction_links` 는 `transactions` 의 **두 번째 자식**이자 자기참조 M:N 간선.
- `parties` 를 경유인으로 **직접** 참조한다. 역할 테이블(`transaction_parties`)을
  거치지 않는다 — 경유인은 그 거래의 당사자가 아니라 자금이 스쳐간 계좌이기 때문.
- `cases` 를 직접 참조한다. 다른 4개 테이블처럼 `case_id` 를 들고 다녀 필터링한다.
- 링크의 `case_id` ≠ 양 끝 거래의 `case_id` → `link_case_mismatch` 플래그.
  교차 사건 링크는 사실상 입력 오류다.

### 4.1 로더 변경 (구현 시)

```python
# Dataset.load()
tx_links=_rows(d / "transaction_links.csv"),
```

`Dataset` 에 `outgoing_links(tx_id)` / `incoming_links(tx_id)` 헬퍼 추가.
`parties_of()` 와 동일하게 존재하지 않는 `transaction_id` 참조는 걸러내되,
**조용히 버리지 말고 플래그를 남긴다** (README §8 "채무자 본인을 데이터로 표현하는
방식이 사건마다 다르다" 항목과 같은 교훈).

## 5. 순환 참조 방지

네 겹으로 막는다. 어긋남이 조용히 넘어가지 않게 한다.

**1. 시간순 제약 (1차 방어).** 모든 간선은 `date(from) ≤ date(to)` 를 만족해야
한다. 시간은 앞으로만 흐르므로 이것만으로 대부분의 순환이 구조적으로 불가능하다.
위반 시 로드 단계에서 `link_reversed_time` 오류.

**2. 동일자 처리.** `date(from) == date(to)` 인 링크는 타이브레이커가 필요하다.
`transactions` 에 선택적 `intra_day_seq`(정수)를 두고 `(date, intra_day_seq)` 로
전순서를 만든다. 진짜 당일 왕복거래도 이 전순서로 선형화되며, 되돌아오는 간선은
순서 위반으로 거부되어 **입력이 비순환 표현을 강제당한다.**

**3. 자기 루프 금지.** `from_transaction_id != to_transaction_id`.

**4. 그래프 검증 (백스톱).** 로드 시 DFS / 위상정렬로 사이클을 탐지한다. 발견되면
관련 `link_id` 를 나열하며 `TransactionLinkCycle` 로 즉시 실패한다
(`UnimplementedPredicate` 와 같은 태도). 중복 간선 `(from, to, link_type)` 유일성
검사와 역방향 `(to, from)` 모순 검사도 여기서 한다.

**5. 순회 깊이·시간창 상한.** DAG 라도 `funds_circled_back` 탐색의 최대 홉 수와
최대 시간창을 둔다. 10홉짜리 추적은 정황에 불과하다. 이 값들은 **조문/운영값이므로
코드가 아니라 `art391_4_gratuitous.yaml` 에** 둔다.

```yaml
transaction_links:
  fund_trace_types: [fund_trace, shared_asset, same_instrument]
  max_trace_hops: 5
  max_trace_window_days: 90
```

> **핵심:** "환류"라는 결론은 *가치 소유의 순환*(채무자 → 경유인 → 관계인)이지
> `transaction_links` 그래프의 순환이 아니다. 링크 그래프는 항상 DAG 로 유지하고,
> 순환은 룰이 경로의 끝단을 보고 판정한다.

## 6. 술어가 이 테이블을 소비하는 방식 (설계만)

```
funds_circled_back(tx) :=
  transaction_links 를 fund_trace_types 로 필터한 DAG 에서
  tx 를 포함하는 경로가 존재하고 (max_trace_hops · max_trace_window_days 이내),
  그 경로의 한쪽 끝은 채무자로부터의 가치 유출,
  다른 쪽 끝의 ultimate_beneficiary(또는 counterparty)가
    related_party.verdict == "related" 이거나 채무자 본인
```

- `confirmed = N` 링크도 신호는 점등하되, 링크의 `confirmed` 값을 출력의
  `⚠ 확인 필요` 로 전달한다. 시스템이 "의심"을 "확정"으로 보이지 않게 한다.
- 채무자 본인 판정은 README §8 "채무자 본인을 데이터로 표현하는 방식" 항목이
  먼저 정리되어야 한다 (`ultimate_beneficiary == case.debtor_id`).
