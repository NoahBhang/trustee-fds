# trustee-fds

파산관재인의 부인권 검토를 지원하는 **설명가능한 조사 대상 선별 시스템** 이다.

법률 판단을 자동화하지 않는다. 관재인이 놓치기 쉬운 거래를 찾아내고, 그 이유와 증거를
법률요건별로 정리해 제시하는 것이 목적이다.

> **면책**  이 저장소는 연구 및 포트폴리오 목적의 자료이며 법률의견서가 아니다.
> 개별 사건의 부인권 행사 여부는 사건 기록, 증거, 최신 법령·판례 및 담당
> 파산관재인의 법률적 판단에 따라 결정되어야 한다.
>
> 특히 `rules/related_party.yaml` 의 **특수관계인 분류는 관련 시행령 원문과
> 대조되지 않은 초안** 이다(`status: draft`). 실제 사건에 사용해서는 안 된다.

---

## 1. 이 시스템이 하는 일과 하지 않는 일

| 한다 | 하지 않는다 |
|---|---|
| 법정 시간 창과 행위 유형으로 후보 선별 | 부인권 성립 여부의 자동 판정 |
| Value Out ↔ Value In 비대칭 산출 | 대가비율을 법정 기준으로 선언 |
| 회수 기대액 기준 우선순위 정렬 | 점수를 승소 확률로 제시 |
| 확인 사실과 미확인 사실의 구별 표시 | 증거 부재를 무상성으로 단정 |
| 사람이 검증해야 할 항목의 명시 | 공정가치·지급정지일의 종국적 확정 |
| 평가액 미상 항목의 별도 분리 표시 | **부작위의 탐지** (§8 참조) |

시스템의 성공 기준은 적발률이 아니다. **관재인이 더 짧은 시간에 누락 없이 증거를
확인하고, 법률요건별 판단 근거를 재현할 수 있는가** 이다.

---

## 2. 왜 룰 기반인가

머신러닝이 아니라 룰 기반을 택한 것은 기술적 후퇴가 아니라 **목적함수의 차이** 다.

| | 은행 FDS | 본 시스템 |
|---|---|---|
| 시간 방향 | 예측 | 소급 추론 |
| 분석 시점 | 거래 발생 시점 | 파산선고 시점(고정) |
| 우선 지표 | 정밀도 | 금액가중 재현율 |
| 최종 산출물 | 차단 결정 | 법정 논거 |
| 산출물의 소비자 | 기계 | 사람(관재인·법원) |

법정에서 "모델이 그렇게 판단했습니다"는 논거가 되지 않는다. 요구되는 것은
**말로 설명되고 조문으로 역추적되는 근거** 다.

또한 이 도메인에서는 판단 기준이 데이터에서 귀납될 필요가 없다. 채무자회생법
제391조가 이미 요건을 명시적으로 열거하고 있기 때문이다. 문제는
"패턴을 학습하는 것"이 아니라 **"조문을 실행 가능한 형태로 번역하는 것"** 이다.

## 3. 아키텍처

```
  입력  cases.csv · transactions.csv · parties.csv · transaction_parties.csv
     │
     ▼
┌───────────────────────────────────────────────────────┐
│ 1층  판정 엔진                                        │
│   rules/related_party.yaml → 관계 판정 · 소급기간     │
│   rules/art391_4_gratuitous.yaml → 시간 창 · 행위유형 │
└───────────────────────────────────────────────────────┘
     │  후보 집합 (+ 근거 조문 태그)
     ▼
┌───────────────────────────────────────────────────────┐
│ 2층  경제적 실질                                      │
│   Value Out / Value In · 대가비율 · 염가 판정         │
└───────────────────────────────────────────────────────┘
     │
     ▼
┌───────────────────────────────────────────────────────┐
│ 3층  정렬                                             │
│   ① 회수 기대액 미상 — 평가 필요   ← 위에 표시        │
│   ② 회수 기대액 순                                    │
└───────────────────────────────────────────────────────┘
     │
     ▼
┌───────────────────────────────────────────────────────┐
│ 4층  설명 생성                                        │
│   사실 / 미확인 사항 구별 · ⚠ 확인 필요 항목          │
└───────────────────────────────────────────────────────┘
```

### 룰은 코드가 아니라 데이터다

판정 로직을 파이썬 `if` 문에 넣지 않고 `rules/*.yaml` 에 둔다. 이유는 셋이다.

1. 법령이 개정되면 YAML만 수정한다.
2. 판정 결과에서 조문으로 역추적된다.
3. **법률 전문가가 코드를 읽지 않고 룰을 검토할 수 있다.**

세 번째가 핵심이다. 각 룰 파일 상단에는 법률 검토 확인란이 있다.

### 두 가지 설계 원칙

**사실은 데이터, 판단은 룰.**  `parties.csv` 는 "배우자다", "지분 62% 보유"라는
사실만 담는다. 그것이 특수관계인에 해당하는지는 `related_party.yaml` 이 판정한다.

**입력에 결론을 적지 않는다.**  `action_type` 은 `sale`(매각)이지
`undervalue_sale`(염가매각)이 아니다. 염가 여부는 대가비율을 계산해야 나오는
결론이며, 그것을 입력에 적으면 시스템이 아니라 사람이 판정한 것을 되읽게 된다.

## 4. 데이터 모델

네 개 테이블로 정규화되어 있다.

```
cases ──< transactions ──< transaction_parties >── parties
```

### `cases`

| 필드 | 설명 | 비고 |
|---|---|---|
| `case_id` | 사건 식별자 | |
| `petition_date` | 파산신청일 | 기록상 확정 |
| `suspension_of_payment_date` | 지급정지일 | **다투어지는 값** |
| `suspension_date_basis` | 지급정지일 특정 근거 | |
| `suspension_date_confirmed` | 확정 여부 | 민감도 분석 트리거 |
| `adjudication_date` | 파산선고일 | 창의 상한 후보 (§8) |

`suspension_of_payment_date` 는 확정값이 아니라 **시나리오 변수** 로 다룬다.
아래는 `data/sample` 로 실제 산출한 값이다.

```
지급정지일 시나리오 (CASE-001, 파산신청일 2025-11-14 고정)
  미특정 (파산신청일만)   후보 10건   회수 기대액 1,177,000,000원
  2025-08-20             후보 13건   회수 기대액 1,320,000,000원
  2025-05-01             후보 16건   회수 기대액 1,375,000,000원
  2025-01-10             후보 16건   회수 기대액 1,375,000,000원
```

관재인이 "지급정지 시점을 앞당겨 주장할 실익"을 즉시 볼 수 있게 하는 것이 목적이다.
2025-05-01 이전으로는 결과가 변하지 않으므로, 그 지점을 넘겨 다툴 실익은 없다.

### `parties`

관계는 **사실** 로만 기록한다. 특수관계인 해당 여부는 `related_party.yaml` 이 판정한다.

| 필드 | 설명 |
|---|---|
| `party_id`, `case_id`, `display_name`, `party_type` | |
| `relation_type` | 배우자 / 직계비속 / 형제 / 인척 / 계열회사 등 — **사실** |
| `relation_valid_from`, `relation_valid_to` | **관계는 변한다.** 이혼·퇴임·지분매각 |
| `relation_basis`, `relation_source` | 증빙 |

판단 기준일은 파산선고 당시가 아니라 **행위 당시** 다.

### `transaction_parties`

거래와 당사자는 다대다다. 역할을 행으로 분리한다.

| 필드 | 설명 |
|---|---|
| `transaction_id`, `party_id` | |
| `role` | `legal_counterparty` / `principal_debtor` / `ultimate_beneficiary` |
| `share_ratio`, `share_amount` | 상대방이 복수인 경우의 배분 |

**소급기간 분기는 오직 `legal_counterparty` 의 관계만 본다.**
`principal_debtor` 의 특수관계는 조사 신호일 뿐 기간을 바꾸지 않는다.
대법원 2009. 2. 12. 선고 2008다48117.

### `transactions`

| 필드 | 설명 |
|---|---|
| `transaction_id`, `case_id`, `transaction_date` | |
| `action_type` | 사실만 기록. `sale`, `gift`, `third_party_guarantee` 등 |
| `asset_fair_value` | 출연재산의 합리적 가치 (null 허용) |
| `fair_value_source` | 감정 / 시세 / 거래사례 / 추정 |
| `liability_increase_value` | 보증 등으로 증가한 채무 |
| `waived_right_value` | 포기한 권리의 가치 |
| `consideration_contractual` | 계약서상 명목 대가 |
| `consideration_paid` | 실제 지급이 확인된 대가 |
| `payment_verified` | 금융자료 대조 여부 |
| `debtor_direct_benefit_value` | 채무자에게 귀속된 직접 이익 |
| `benefit_realizability` | 이익의 실현 가능성 |
| `necessity_evidence` | 상당성 자료 |
| `contrary_evidence` | 정상거래를 지지하는 반대 증거 |
| `source`, `note` | |

**파생 필드는 저장하지 않는다.**  `days_before_event` 같은 값은 지급정지일이 바뀌면
즉시 낡는다. 실행 시 계산한다.

`asset_fair_value` 의 결측은 예외가 아니라 **기본 상태** 다. 결측을 0으로 대체하지
않으며, 결측 항목은 정렬에서 밀어내지 않고 별도 섹션으로 올린다.

## 5. 현재 범위 (Phase 1)

- 대상 조문: **제391조 제4호(무상부인) 하나만**
- 입력: 정제된 CSV가 주어졌다고 가정
- 출력: CLI 텍스트 리포트

제1호~제3호는 모두 수익자의 악의를 요건으로 하며, 그것은 거래 데이터에 존재하지
않는다. 제4호는 성립 요건에 수익자의 주관적 요건이 없어 **거래 데이터와 당사자
관계 자료만으로 시기적·객관적 요건을 검토할 수 있다.**  다만 유해성 요건과 상당성
항변은 별도로 존재하므로, 시스템은 요건 충족을 부인 성립으로 표현하지 않는다.

특수관계 판정 역시 상당수가 `verify`(시행령 대조 필요)로 남는다. 거래 데이터만으로
끝나는 작업이 아니다.

파서를 먼저 만들지 않는 이유는 **디버깅 경계** 때문이다. 판정 엔진이 굳기 전에
파서를 붙이면 결과가 이상할 때 파싱이 틀린 건지 룰이 틀린 건지 구분할 수 없다.

## 7. 검증 전략

라벨이 붙은 데이터셋이 세상에 존재하지 않으므로 PR-AUC 같은 지표를 쓰지 않는다.
대신 **각 케이스가 무엇을 검증하는지** 를 명시하고, 실제 판례를 기대값으로 삼는다.

### `target_stage` — 케이스는 자기가 검증하려는 단계까지 도달해야 한다

앞 단계에서 걸러지는 케이스는 뒷 단계를 검증하지 못한다. 통과하더라도 아무것도
증명하지 않는다. `expected_results.csv` 의 `target_stage` 가 이를 감시한다.

| 값 | 검증 대상 |
|---|---|
| `temporal` | 시간 창 · 소급기간 분기 |
| `action` | 행위 유형 필터 · 라우팅 |
| `party` | 당사자 역할 분리 · 복수 상대방 |
| `economic` | Value Out/In · 대가비율 |
| `ranking` | 결측 항목의 분리 표시 |
| `signal` | 신호 중첩 |

실제로 두 건이 이 기준에서 무력했다.

- **T101** — 1년 특칙 오적용을 잡으려는 케이스였으나 6월·12월 창 **양쪽 모두 안** 에
  있어, 오답이어도 통과했다. 두 창 사이(2024-07-11 ~ 2025-01-11)에 놓은 T107을
  대조군으로 추가했다.
- **T015** — 정상 매각이 대가비율에서 걸러지는지 보려는 케이스였으나, 시간 창
  **밖** 이라 3단계에 도달하지 못했다. 창 안으로 옮겼다.

> **분기를 검증하는 케이스는 반드시 분기의 경계 사이에 놓여야 한다.**

### 판례 기반 대조

각 판결의 사실관계를 입력 형식으로 옮기고, 후보 검출 결과를 법원의 결론과 대조한다.

```
T-2014다765    | 무상성 인정   | 검출 ✓
T-2008다48117  | 1년 특칙 부정 | 6월 창 적용 ✓
T-정상매매      | 부인 부정     | 3단계에서 제외 ✓
```

**부인이 부정된 사안이 특히 중요하다.** 오탐의 경계를 정의하기 때문이다.

경계 사례로 반드시 포함할 것:

- 자기 채무의 정상 변제 (순재산 중립 → 제4호 대상 아님)
- 자기 채무의 **과다** 변제 (초과분은 실질적 무상 → 배제하지 않고 3단계로)
- 신규차입과 교환적으로 제공된 담보 (직접 대가 귀속)
- 상속포기 (인적 결단 → 일반적 부인 대상과 구별)
- 상속재산분할협의상 지분 포기 (부인 검토 대상)
- 적정가 매각 (합리적 범위의 가격 차이)

## 8. 열린 질문과 한계

### 시간 창의 상한이 어디인가

조문은 "지급정지 또는 파산신청이 있은 후"로 열려 있어 문언상 종기가 없다. 파산선고
후에는 관리처분권이 관재인에게 이전되므로 사실상 선고일이 상한으로 기능할 것으로
보이나, 확인이 필요하다.

현재 구현은 상한을 **하드 필터로 쓰지 않고** 별도 표시만 한다
(`upper_bound.behavior: soft`).

### 부작위는 탐지할 수 없다

시효중단 미조치, 지급명령 이의 미제기 같은 부작위도 부인 대상이 될 수 있다.
그러나 **부작위에는 거래 기록이 없다.**  CSV에 존재하지 않는 행을 스캔으로 찾을
방법은 없다.

이는 스키마를 고쳐서 해결되는 문제가 아니다. 채권 목록과 소멸시효 만료일을 별도로
관리하여 "기대되는 행위가 없었던 시점"을 역으로 찾아야 하며, 완전히 다른 자료
구조가 필요하다. Phase 1 범위 밖으로 둔다.

### 행위 유형에 따라 대가비율의 의미가 다르다

현재 `triage_bands` 는 모든 행위에 같은 밴드를 적용한다. 매각에서는 타당하지만
보증에서는 그렇지 않다.

샘플의 T103이 이 문제를 드러낸다. 보증채무 300,000,000원에 보증료 12,000,000원을
실제로 수령한 사안인데, 대가비율 0.04로 계산되어 `high` 로 분류된다. 그러나
보증료율은 원래 한 자릿수 퍼센트이므로, 이 비율만으로 무상성을 의심할 수는 없다.

두 가지가 얽혀 있다.

1. **액면과 기대가치의 혼동.**  `liability_increase_value` 를 룰에서는 "채무 증가의
   기대가치"로 정의했으나, 실제로 채워 넣기 쉬운 값은 보증채무 액면이다. 보증인이
   실제로 부담하게 될 금액은 주채무자의 변제 능력에 달려 있어 액면과 크게 다르다.
2. **밴드의 단일 적용.**  매각의 대가비율과 보증의 대가비율은 같은 척도가 아니다.

해결하려면 `liability_increase_face` / `liability_increase_expected` 로 필드를 쪼개고
행위 유형별 밴드를 두어야 한다. 스키마 변경을 수반하므로 현재는 열려 있고,
T103은 불일치를 감춘 채 통과시키지 않고 **`high` 로 기록해 두었다.**

### 스키마가 아직 표현하지 못하는 것

- 거래 간 연결 (자금 환류) — 로드맵 4단계
- 담보 제공의 성격: 재산 유출이 아니라 **책임재산의 위험 노출**
- 포기한 채권의 **액면가와 회수가능 가치** 의 구별
- 보증채무의 **액면과 기대가치** 의 구별 (위 항목과 같은 뿌리)

## 10. 실행

**Python 3.9 이상** 이 필요하다. 외부 의존성은 없다(표준 라이브러리만 사용).

### macOS · Linux

```bash
python3 src/cli.py
```

### Windows

윈도우에는 `python3` 명령이 없다. `python` 또는 `py` 런처를 쓴다.

```bat
python src/cli.py
```

```bat
py -3 src/cli.py
```

리포트 출력 후 `data/sample/expected_results.csv` 와 대조한다. 불일치가 있으면
종료 코드 1을 반환한다.

### 윈도우 한국어 콘솔의 인코딩

이 리포트는 `—`(U+2014) 와 `⚠`(U+26A0) 을 쓴다. 한국어 윈도우의 기본 콘솔
인코딩인 cp949 에는 두 글자가 모두 없어, 아무 처리도 하지 않으면 리포트 첫 줄에서
`UnicodeEncodeError` 로 죽는다. 그래서 `src/cli.py` 는 시작 시 표준 출력·표준
오류를 UTF-8 로 재설정한다.

이것으로 예외는 사라지지만, **화면에 글자가 제대로 보이는지는 콘솔의 코드페이지에
달려 있다.** Windows Terminal 이나 최신 PowerShell 에서는 그대로 표시된다.
구형 `cmd.exe` 에서 글자가 깨진다면 실행 전에 코드페이지를 UTF-8 로 바꾼다.

```bat
chcp 65001
python src/cli.py
```

### 룰과 코드의 결합 지점

`when` 표현식을 해석하는 완전한 표현식 언어는 만들지 않았다. 대신 술어를
**id 로 등록** 하고, YAML 에 선언된 id 중 구현이 없는 것이 있으면
`UnimplementedPredicate` 로 즉시 실패한다.

조문에서 나오는 값(소급기간, 기준 사건, 행위 유형 목록, 임계값, 정렬 구획)은
전부 YAML 에서 읽는다. 술어의 *판단 로직* 만 코드에 있고, 그 존재 여부는
룰이 강제한다. 완전한 데이터 주도는 아니지만, 어긋남이 조용히 넘어가지는 않는다.
